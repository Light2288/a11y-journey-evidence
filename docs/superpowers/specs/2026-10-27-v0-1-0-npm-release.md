## Problem and Current Behavior

The public GitHub repository contains the completed dialog and form increments and the merged Space-key correction, but its package metadata still identifies the initial Batch 1 prerelease. Root `package.json` declares `0.1.0-batch.1` and `private: true`; the root lockfile and consumer tarball example retain the same version. The README describes tarball-only distribution and excludes registry publication from its historical delivery scope.

`private: true` prevents npm publication; it does not control GitHub repository visibility. The package has ESM exports for the fixture and reporter, compiled declarations, an explicit packed file list, MIT licensing, and an existing packed-consumer verification command. Repository/homepage/issue metadata is currently absent.

Inspection on 2026-10-27 found a clean `main` tracking `origin/main` at `711077e543f05da82d6daf74b9c179bb69db4be1`. A public registry lookup for `a11y-journey-evidence` returned E404; this does not reserve the name or guarantee publication rights. `npm whoami --registry=https://registry.npmjs.org` returned ENEEDAUTH. No registry write was attempted.

The preceding read-only assessment found supporting evidence for all 17 original release criteria within the documented experimental scope. Its verification is historical input for this chore; publication requires fresh checks against the release artifact.

## Desired Outcome and Delivery Boundary

**Wider direction:** Make the completed experimental v0.1 package available to Playwright users and gather real usefulness feedback before selecting further product work.

**Selected increment:** Prepare and publish the existing package as public npm package `a11y-journey-evidence@0.1.0`, using the normal `latest` distribution tag, and verify an independent installation from the registry. Keep the product described as experimental despite the non-prerelease version number.

**Uncertainty:** Publication and registry-consumer verification establish distribution usability. They do not establish external usefulness, wider compatibility, screen-reader behavior, or accessibility conformance.

**Necessary safeguards:** Consistent release metadata and documentation, a reviewed and verified tarball, fresh existing checks, npm authentication and name/ownership checks, and a durable release record that separates preparation from confirmed publication. Publish the exact verified artifact rather than rebuilding an unverified artifact during upload.

**Deferred work:** New features, API redesign, dependency upgrades, broader browser/host/CI verification, automated release pipelines, external outreach, and feedback-driven improvements. No later increment is specified or authorized here.

**Boundary rationale:** Release metadata, onboarding, artifact verification, publication, and registry installation form one independently verifiable distribution outcome. The completed implementation does not need another feature increment before that outcome can be evaluated.

## Approaches

- **Publish the completed scope as experimental v0.1.0 — selected.** Align the version with the completed release scope and simplify installation while retaining explicit compatibility and evidence limits. The user approved this recommendation.
- **Continue tarball-only evaluation.** Avoids registry publication but adds installation friction; the assessment identified no concrete technical blocker requiring this delay.
- **Publish another batch prerelease.** Provides registry access but retains an increment label that no longer describes the completed v0.1 scope. No additional prerelease capability gate was identified.
